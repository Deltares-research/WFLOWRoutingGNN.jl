# WflowRoutingGNN.jl

The goal of this project is to implement a machine-learning emulator of the river-routing algorithms used in the hydrological model Wflow.jl. The main focus is for the emulator to be computationally faster with limited memory footprint than Wflow.jl while maintaining comparable accuracy.

The emulator should also maintain some physical consistency, but without resorting to elaborate traditional numerical schemes. Of particular importance are:
- Mass Conservation
- Stable long-term behaviour
- Robustness to unseen forcing conditions

## Design

The project uses a Graph Neural Network (GNN) to emulate the behaviour of the river routing modules of Wflow.jl. The graph of the GNN matches the river in Wflow as defined by its river mask and local drainage direction data. Training data is generated by running a mutli-decadal Wflow simulation.

The mass balance is enforced through a GNN layer called at the end of each forward model pass. This aims to inject physical consistency in the model and to aid with the long-term stability and generalizability.

Experiments in the project are run by calling the appropriate Julia script from the command line with a config TOML file as argument. Template config files are provided in the `experiments` directory

### Current architecture

The sections below summarise the *current implemented state*. Full reasoning
lives in [DECISIONS.md](DECISIONS.md) and the research notes under `docs/notes/`.

- **Four-stage pipeline.** The workflow is split into four independently runnable
  stages — **preprocess → train → infer → analyze** — that exchange on-disk
  artifacts (`prep/`, `model/`, `output/`, `metrics/`+plots). Running all four
  back-to-back reproduces every artifact the old monolithic `run_wflow_gnn`
  produced. Stages are dispatched through a `Stage` type hierarchy
  (`run_stage(::PreprocessStage, …)` …) and driven from the CLI by
  `scripts/pipeline.jl <prep|train|infer|analyze|all>`. Inference writes only
  gridded wflow-faithful NetCDF; analysis reconstructs node arrays from those
  NetCDFs via the prep-owned node↔cell mapping, so any analysis (including
  mass-balance residuals) can run post-hoc on any trained model.
- **Encode–process–decode GNN with a physics decoder.** Nodes are river cells,
  edges follow the local drainage direction. Neighbour aggregation
  `out[i] = Σ_{j→i} h[:,j]` is implemented as a sparse matrix–dense multiply
  (`SparseConv`, cuSPARSE SpMM) rather than scatter-gather — the fastest path on
  GPU. Batched training uses a precomputed block-diagonal adjacency
  (`precompute_batched`, built on CPU before moving to GPU).
- **Hard mass balance (the `ThetaKinematicWave` formulation).** The decoder predicts only the
  discharge increment `Δq` (`out_dim = 1`); `river_h` is derived analytically
  from the kinematic-wave water balance every step, so conservation is exact by
  construction. The discretisation is **fully implicit** (all fluxes at `t+1`,
  verified against real Wflow output), blended by a configurable `mb_theta`
  (default `1.0`). The layer is a *rollout governor*: with it, rollouts stay
  finite where the unconstrained model overflows. Mass-balance code lives in its
  own `src/massbalance.jl` (+ `src/sparse_ops.jl` for the shared sparse adjoint);
  formulations are a `MassBalanceFormulation` dispatch hierarchy
  (`ThetaKinematicWave`, or `NoMassBalance` for models trained without a layer),
  so new formulations toggle via a single `mb_formulation` config key rather than
  `if/else` branches.
- **Normalisation.** Per-variable z-score plus a physical postscale
  (`river_q` area-normalised to specific discharge; `river_h` scaled by `w·l/A`),
  with statistics fit on the training split only. The MB layer evaluates physics
  in physical units; positivity floors are applied in physical units inside the
  layer.
- **Training.** A rollout-length curriculum (`steps = [1,2,5,8,10]`) with a
  warm-restart (SGDR-style) learning-rate schedule — cosine decay within each
  phase, linear warmup and a geometrically shrinking peak at each restart —
  and BPTT via `Zygote.checkpointed`. A custom `_topology_mul` adjoint keeps the
  adjacency out of the backward pass (the key out-of-memory fix). Gradients flow
  through the mass balance, re-weighted (`h_loss_weight = σ_h/(dt·σ_q)`) so the
  `q` and `h` channels have comparable magnitude. An autotune path
  (LR-range-test + batch-size estimator) can size the LR and batch before a run.
- **Losses & evaluation.** MSE by default, with an optional per-node
  peak-weighted Huber loss. Evaluation produces autoregressive rollouts, a
  water-volume storage/budget diagnostic, longitudinal upstream timeseries, and
  mass-balance residual diagnostics, written as gridded NetCDF + metrics TOML.

### Known limitations

- **Conditional rollout instability at stiff high flows.** Discharge `q` is a
  free state in the loop; its Jacobian can amplify (`ρ(J) > 1`), so rollouts from
  stiff high-flow anchors can still diverge even though benign starts stay
  bounded. This is the main open stability problem (tracked in TODO.md); the
  mass-balance redesign notes propose Muskingum / continuity-readout formulations
  that remove `q` from the loop.
- **Manning rating is only loosely valid at daily resolution** and is therefore
  **not** used as a hard constraint (daily-averaging a nonlinear law breaks under
  unsteady / overbank flow).

## Evaluation Metrics

Plots are written to a run's `plots/` directory (metrics CSV/NetCDF alongside in
`metrics/`/`output/`). The **train** stage writes training-curve diagnostics; the
**analyze** stage writes rollout/skill diagnostics.

Train stage (`pipeline.jl`):

- `losses.png` — training vs validation loss curves (1-step and rollout, with grad-norm / LR / curriculum-step overlays).
- `amplification.png` — the per-epoch `q→h` error amplification factor (mass-balance runs only), tracking how `q` error propagates into `h`.
- `fixed_horizon.png` — per-epoch fixed-horizon validation discharge RMSE and peak ratio (overall and high-flow), a stable rollout-skill signal across epochs.

Analyze stage (`analysis.jl`):

- `validation.mp4` — animated predicted-vs-true gridded `river_q`/`river_h` fields over the split (and `validation_daterange.mp4` for the optional date-range window).
- `downstream_timeseries.png` — predicted vs true discharge timeseries at successive downstream points along the main stem (and `downstream_timeseries_daterange.png` for the date-range window).
- `spatial_metrics.png` — per-cell maps of rollout error metrics across the domain, one row per state variable with these panels:
  - `rmse` — per-cell root-mean-square error over the rollout.
  - `bias` — mean signed error (pred − truth); positive = over-prediction.
  - `overpred_freq` — fraction of timesteps the cell over-predicts.
  - `peak_err` — difference between the predicted and true series maxima (peak over/under-estimation).
  - `peak_lag` — cross-correlation lag (in Δt) of best alignment, i.e. timing error of the peak/signal.
  - `nbias` — bias normalised by the truth's standard deviation (dimensionless, cross-cell comparable).
  - `nse` — Nash–Sutcliffe efficiency of the per-cell timeseries.
- `q_overprediction_vs_ramp.png` — scatter of discharge over-prediction against the rising-limb ramp rate, testing whether error grows with how fast flow is rising.
- `mb_diagnostics.png` — mass-balance residual / depth-floor diagnostics over the rollout (mass-balance models).
- `volume_budget.png` — the domain water-volume storage and budget (inflow − outflow − storage change) over time, with its drift/PBIAS.

Spatial-evaluation helper (`spatial_eval`, per split):

- `<split>_spatial_metrics.png` — the per-cell error maps above, computed for a named split.
- `<split>_q_overpred_vs_ramp.png` — the over-prediction-vs-ramp scatter for a named split.

Subcatchment error attribution (`attribution.jl`, per split):

- `<split>_subcatch_error_map.png` — maps of each subcatchment's specific local error and its local share of the outlet error (injected vs advected).
- `<split>_subcatch_mainstem.png` — advected vs locally injected RMS error along the main stem, showing where error enters vs compounds.
- `<split>_subcatch_attributes.png` — the strongest Spearman rank correlations between subcatchment attributes and local error injection.

## Project structure

### Code & Data

```
src/
|- WflowRoutingGNN.jl   Main entrypoint, defines public functions etc.
|- schema.jl            Variable/NetCDF schema definitions
|- preprocess.jl        Preprocessing of Wflow data and graph creation
|- sparse_ops.jl        Shared sparse message-passing op + custom autodiff rrule
|- massbalance.jl       Mass-balance formulations (dispatch hierarchy) + layer
|- gnn.jl               Generic GNN layer definitions (SparseConv, WflowGNN)
|- strategy.jl          Train strategies, loss functions etc.
|- training.jl          Main training loop
|- pipeline.jl          Stage functions: preprocess/train/infer + PrepBundle I/O
|- analysis.jl          Stage 4 analysis (analyze_run, spatial_eval, regen)
|- run.jl               Stage orchestration (Stage hierarchy, run_wflow_gnn)
|- tune.jl              LR-range-test / batch-size / autotune toolkit
|- hparsearch.jl        Hyperparameter search functionality
|- rollout.jl           Functions for autoregressive rollout of simulation
|- postprocess.jl       Regrid, eval metrics, layer-free MB residual diagnostic
|- consistency.jl       Layer-free MB routing/residual + wflow-output checks
|- plot.jl              Plot functionality

test/                   Main tests
test_data/              Data to use for tests
scripts/                Thin CLIs (pipeline, train, hparsearch, benchmarks, util)
scripts/oneoff/         Archived one-off analysis scripts
models/                 Wflow models used to generate training data
experiments/            Templates for config TOML files; Archive of past experiments
```
